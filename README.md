## 1. Problem Statement and Research Objectives

Modern enterprises increasingly rely on distributed, cloud-based architectures, which has driven the growth of **Shadow IT** — SaaS applications and cloud storage used by employees without institutional oversight — and, more recently, **Shadow AI**, the unsanctioned use of AI tools and unmonitored API endpoints. Traditional, signature-based Data Loss Prevention (DLP) systems are frequently bypassed by these tools because they mimic legitimate traffic or use encrypted channels, leaving a critical visibility gap that both malicious insiders and well-meaning employees can exploit to exfiltrate data without detection.

This project investigates whether **behavioral anomaly detection** — built from authentication, file-access, and web-browsing metadata rather than payload inspection — can close this gap.

**Research Questions:**
1. What are the primary technical gaps in standard DLP systems that allow unauthorized data transfers via unsanctioned cloud storage and Shadow AI tools?
2. Which user behavior and network traffic metrics are most statistically correlated with corporate data exposure incidents caused by human error?
3. How effectively can supervised machine learning classifiers detect unauthorized cloud data exfiltration compared to unsupervised anomaly detection?

**Objective:** Design, implement, and critically evaluate a reproducible behavioral-detection pipeline — covering feature engineering, supervised and unsupervised modeling, threshold optimization, and robustness testing — using a real insider-threat dataset, and assess its practical value as a triage tool for a Security Operations Center (SOC).

## 2. Dataset Description

- **Source:** CERT Insider Threat Dataset, Release 3.2 (CERT r3.2)
- **Logs used:** `logon.csv`, `file.csv`, `http.csv`, plus the associated ground-truth answer files identifying malicious users
- **Unit of analysis:** user-week behavioral profiles, aggregated from event-level logs
- **Class balance:** extremely imbalanced — 68,571 benign vs. 11 malicious user-week observations (~0.016% positive class), from exactly 2 confirmed malicious insiders
- **Engineered features:** `logon_frequency`, `logoff_frequency`, `unique_pc_count`, `unique_files_accessed`, `file_access_frequency`, `unique_pc_file`, `http_request_frequency`, `unique_domains_visited`, `risky_domain_visit_count`, and after-hours variants (`after_hours_logon`, `after_hours_http`, `after_hours_file`)

> The raw CERT dataset is not redistributed in this repository. See [Installation and Execution](#4-installation-and-execution) for how to obtain it.

### 4.4 Reproducing the Pipeline

Run all cells top to bottom. The notebook is organized into 22 sequential sections:

1. **Setup & Imports, Configuration** (Sections 1-3)
2. **Feature Engineering** (Section 4): builds user-week behavioral profiles from `logon.csv`, `file.csv`, `http.csv` (the latter streamed in chunks for memory safety)
3. **Ground-Truth Labeling** (Sections 5-6): labels each user-week as malicious/benign from the CERT answer files
4. **Exploratory Data Analysis** (Section 7): class distribution, correlation heatmap, feature distributions
5. **Modeling** (Sections 9-20): group-based (user-level) train/test split, a reusable F1-threshold-optimization helper, Random Forest given full standalone treatment, a feature-separability diagnostic, SMOTE + swapped-malicious-user robustness testing, a six-model comparison (Random Forest, Logistic Regression, Decision Tree, Isolation Forest, Local Outlier Factor, One-Class SVM), and Isolation Forest - the final recommended model - given the same full standalone treatment
6. **Model Persistence** (Section 22): saves the trained Random Forest and Isolation Forest models plus the fitted `StandardScaler` via `joblib`

**Where outputs go:** each `plt.savefig(...)` call writes a figure to the notebook's working directory, and each results table is written via `.to_csv(...)` to `<base_path>/`. ## 5. Summary of Results

| Model | Threshold | Precision | Recall | F1-score | Workload Reduction |
|---|---|---|---|---|---|
| Random Forest | Default (0.50) | 0.0000 | 0.0000 | 0.0000 | 1.0000 |
| Random Forest | Optimized (~0.000) | 0.0002 | 1.0000 | 0.0004 | -0.0002 |
| Logistic Regression | Default (0.50) | 0.0000 | 0.0000 | 0.0000 | 0.9994 |
| Decision Tree | Default (0.50) | 0.0000 | 0.0000 | 0.0000 | 1.0000 |
| Isolation Forest | Default | 0.0000 | 0.0000 | 0.0000 | 0.9996 |
| **Isolation Forest** | **Optimized (0.519)** | **0.0019** | **1.0000** | **0.0039** | **0.8887** |
| Local Outlier Factor | Optimized (-4.319) | 0.0010 | 0.3333 | 0.0020 | 0.9293 |
| One-Class SVM | Optimized (-0.153) | 0.0005 | 0.3333 | 0.0011 | 0.8670 |

**Key findings:**
- Despite ~99.98% Accuracy, the default-threshold supervised classifiers achieved **0% Recall** - they failed to detect any malicious activity, illustrating why Accuracy is misleading under extreme class imbalance.
- Threshold optimization raised Recall to 100% for Random Forest, but at the cost of flagging almost the entire test set as suspicious (near-zero workload reduction).
- **SMOTE and malicious-user-swapped robustness tests** confirmed the supervised failure is a structural limitation - with only 2 confirmed malicious identities, a model trained on one cannot generalize to the other - rather than a fixable tuning or class-imbalance issue.
- The **optimized Isolation Forest** offered the most promising detection-workload trade-off: 100% Recall with ~84-89% workload reduction across both robustness-check split directions, though Precision remained under 1%, meaning it is best suited as a **triage/ranking mechanism**, not a standalone detector.
- Random Forest feature-importance analysis identified `unique_pc_count`, `logoff_frequency`, `unique_files_accessed`, and `logon_frequency` as the strongest behavioral indicators - authentication and resource-access patterns mattered more than raw web-browsing volume.

Full methodology, discussion, and limitations are documented in [`Report/`](./Report).
